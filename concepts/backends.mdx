---
title: "Backends: Configure Cloud and Kubernetes Providers"
description: "Backends connect dstack to cloud providers and Kubernetes for fleet provisioning. Configure VM-based or container-based backends via config file or project UI."
---

Backends tell dstack where to provision compute. A backend represents a connection to a specific cloud provider or Kubernetes cluster, and each dstack project can configure multiple backends simultaneously. dstack supports two types: **VM-based backends**, where dstack natively manages VM provisioning and cluster orchestration, and **container-based backends**, where provisioning is delegated to the cloud provider or Kubernetes.

<Note>
  When using dstack with on-prem servers, backend configuration is not required. Create [SSH fleets](/concepts/fleets) once the server is up.
</Note>

Backends can be configured via `~/.dstack/server/config.yml` or through the project settings page in the UI. If you update `~/.dstack/server/config.yml`, you must restart the server for the changes to take effect.

## VM-based backends

VM-based backends give dstack direct control over cluster provisioning. dstack uses native integrations with each cloud provider to provision instances on demand, manage clusters, and orchestrate container-based runs. This approach offers finer-grained control over provisioning and eliminates the dependency on a Kubernetes layer.

### AWS

There are two ways to configure AWS: using default credentials or an access key.

<Tabs>
  <Tab title="Default credentials">
    If you have default credentials set up (e.g. in `~/.aws/credentials`), configure the backend like this:

    ```yaml ~/.dstack/server/config.yml
    projects:
      - name: main
        backends:
          - type: aws
            creds:
              type: default
    ```
  </Tab>
  <Tab title="Access key">
    Create an access key by following the [AWS guide](https://docs.aws.amazon.com/cli/latest/userguide/cli-authentication-user.html#cli-authentication-user-get). Once you have the Access key ID and Secret access key, configure the backend:

    ```yaml ~/.dstack/server/config.yml
    projects:
      - name: main
        backends:
          - type: aws
            creds:
              type: access_key
              access_key: KKAAUKLIZ5EHKICAOASV
              secret_key: pn158lMqSBJiySwpQ9ubwmI6VUU3/W2fdJdFwfgO
    ```
  </Tab>
</Tabs>

        ```yaml ~/.dstack/server/config.yml

          - name: main

                  type: default
                vpc_name: my-vpc
        ```

        ```yaml ~/.dstack/server/config.yml
        projects:
          - name: main
            backends:
              - type: aws
                creds:
                  type: default
                default_vpcs: true
                vpc_ids:
                  us-east-1: vpc-0a2b3c4d5e6f7g8h
                  us-east-2: vpc-9i8h7g6f5e4d3c2b
                  us-west-1: vpc-4d3c2b1a0f9e8d7
        ```

        For regions without a configured `vpc_id`, enable default VPCs by setting `default_vpcs` to `true`.
      </Tab>
    </Tabs>
  </Accordion>
  <Accordion title="Private subnets">
    By default, dstack provisions instances with public IPs and permits inbound SSH traffic. To use private subnets and provision instances without public IPs, set `public_ips` to `false`:

    ```yaml ~/.dstack/server/config.yml
    projects:
      - name: main
        backends:
          - type: aws
            creds:
              type: default
            public_ips: false
    ```

    Using private subnets assumes that both the dstack server and users can access the configured VPC's private subnets. Private subnets must also have outbound internet connectivity via NAT Gateway, Transit Gateway, or another mechanism.
  </Accordion>
  <Accordion title="Custom OS images">
    By default, dstack uses its own AMI optimized for dstack. To use your own or third-party images, set the `os_images` property:

    ```yaml ~/.dstack/server/config.yml
    projects:
      - name: main
        backends:
          - type: aws
            creds:
              type: default
            os_images:
              cpu:
                name: my-ami-for-cpu-instances
                owner: self
                user: dstack
              nvidia:
                name: 'Some ThirdParty CUDA image'
                owner: 123456789012
                user: ubuntu
    ```

    Both `cpu` and `nvidia` properties are optional; if a property is not set, the corresponding instance types cannot be used. The `owner` is either an AWS account ID or `self` (for the current account). The `user` is the OS user for instance provisioning.

    Image requirements: SSH server on port 22, passwordless sudo for `user`, Docker installed, NVIDIA/CUDA drivers and NVIDIA Container Toolkit installed (for NVIDIA instances), and firewall rules allowing port 22 and internal subnet traffic.
  </Accordion>
</AccordionGroup>

### Azure

There are two ways to configure Azure: using default credentials or a client secret.

<Tabs>
  <Tab title="Default credentials">
    If you have default credentials set up, configure the backend like this:

    ```yaml ~/.dstack/server/config.yml
    projects:
      - name: main
        backends:
          - type: azure
            subscription_id: 06c82ce3-28ff-4285-a146-c5e981a9d808
            tenant_id: f84a7584-88e4-4fd2-8e97-623f0a715ee1
            creds:
              type: default
    ```

    If you don't know your `subscription_id` and `tenant_id`, use [Azure CLI](https://learn.microsoft.com/en-us/cli/azure/install-azure-cli):

    ```shell
    az account show --query "{subscription_id: id, tenant_id: tenantId}"
    ```
  </Tab>
  <Tab title="Client secret">
    Create a client secret using the [Azure CLI](https://learn.microsoft.com/en-us/cli/azure/install-azure-cli):

    ```shell
    SUBSCRIPTION_ID=...
    az ad sp create-for-rbac \
        --name dstack-app \
        --role $DSTACK_ROLE \
        --scopes /subscriptions/$SUBSCRIPTION_ID \
        --query "{ tenant_id: tenant, client_id: appId, client_secret: password }"
    ```

    Once you have `tenant_id`, `client_id`, and `client_secret`, configure the backend:

    ```yaml ~/.dstack/server/config.yml
    projects:
    - name: main
      backends:
      - type: azure
        subscription_id: 06c82ce3-28ff-4285-a146-c5e981a9d808
        tenant_id: f84a7584-88e4-4fd2-8e97-623f0a715ee1
        creds:
          type: client
          client_id: acf3f73a-597b-46b6-98d9-748d75018ed0
          client_secret: 1Kb8Q~o3Q2hdEvrul9yaj5DJDFkuL3RG7lger2VQ
    ```
  </Tab>
</Tabs>

### GCP

There are two ways to configure GCP: using default credentials or a service account.

<Tabs>
  <Tab title="Default credentials">
    Enable GCP application default credentials:

    ```shell
    gcloud auth application-default login
    ```

    Then configure the backend:

    ```yaml ~/.dstack/server/config.yml
    projects:
    - name: main
      backends:
        - type: gcp
          project_id: gcp-project-id
          creds:
            type: default
    ```
  </Tab>
  <Tab title="Service account">
    [Create a service account](https://cloud.google.com/iam/docs/service-accounts-create) and [generate a key](https://cloud.google.com/iam/docs/keys-create-delete) for it, then download the corresponding JSON file.

    Configure the backend by specifying the downloaded file path:

    ```yaml ~/.dstack/server/config.yml
    projects:
    - name: main
      backends:
        - type: gcp
          project_id: my-gcp-project
          creds:
            type: service_account
            filename: ~/.dstack/server/gcp-024ed630eab5.json
    ```

    If you are configuring the `gcp` backend through the project settings page in the UI, specify the contents of the JSON file in `data` instead of `filename`.
  </Tab>
</Tabs>

If you don't know your GCP project ID, use [Google Cloud CLI](https://cloud.google.com/sdk/docs/install-sdk):

```shell
gcloud projects list --format="json(projectId)"
```

### Crusoe

Log into your [Crusoe](https://console.crusoecloud.com/) console and create an API key under your account settings. Note your project ID from the project settings page.

Then configure the backend:

```yaml ~/.dstack/server/config.yml
projects:
- name: main
  backends:
    - type: crusoe
      project_id: your-project-id
      creds:
        type: access_key
        access_key: your-access-key
        secret_key: your-secret-key
      regions:
        - us-east1-a
        - us-southcentral1-a
```

The `regions` field is optional. If not specified, all available Crusoe regions are used.

## Container-based backends

Container-based backends let dstack orchestrate container-based runs on cloud providers that natively support containers, or on Kubernetes. In this case, dstack delegates provisioning to the cloud provider or Kubernetes. Compared to VM-based backends, they offer less fine-grained control over provisioning but rely on the native logic of the underlying environment.

### Kubernetes

dstack can orchestrate container-based runs across both on-prem and managed Kubernetes clusters. To configure the `kubernetes` backend, you need the path to a kubeconfig file, the IP address of a node in the cluster, and a port that dstack will use for proxying SSH traffic.

```yaml ~/.dstack/server/config.yml
projects:
- name: main
  backends:
  - type: kubernetes

    kubeconfig:
      filename: ~/.kube/config

    proxy_jump:
      hostname: 204.12.171.137
      port: 32000
```

<Note>
  To allow the dstack server and CLI to access runs via SSH, dstack requires a node to act as a jump host to proxy SSH traffic into containers. Specify `hostname` (the IP address of any cluster node — GPU or CPU) and `port` (any accessible port on that node). dstack configures and manages the proxy automatically.
</Note>

  <Accordion title="Resources and offers">
    If you use ranges with `resources` (e.g. `gpu: 1..8` or `memory: 64GB..`) in fleet or run configurations, the `kubernetes` backend handles them differently from other backends.

    - For `gpu`, if you specify a range (e.g. `gpu: 4..8`), dstack provisions pods with the GPU count equal to the lower limit (`4`). The upper limit is always ignored.
    - For `cpu`, `memory`, and `disk`, dstack passes the lower and upper limits as Kubernetes [requests and limits](https://kubernetes.io/docs/concepts/configuration/manage-resources-containers/#requests-and-limits). If no upper limit is set, the Kubernetes limit is also not set.

    Example configuration:

    ```yaml .dstack.yml
    type: dev-environment
    ide: vscode

    resources:
      cpu: 32..64
      memory: 1024GB
      disk: 100GB..
      gpu: nvidia:4..8
    ```

    This translates to the following Kubernetes resource spec:

    | Resource            | Request  | Limit     |
    |---------------------|----------|-----------|
    | `cpu`               | `32`     | `64`      |
    | `memory`            | `1024Gi` | `1024Gi`  |
    | `ephemeral-storage` | `100Gi`  | _not set_ |
    | `nvidia.com/gpu`    | `4`      | `4`       |
  </Accordion>

  By default, dstack considers instance offers only from the Secure Cloud. To also include the [Community Cloud](https://docs.runpod.io/references/faq/#secure-cloud-vs-community-cloud), set `community_cloud: true`:

  ```yaml ~/.dstack/server/config.yml
  projects:
    - name: main

        - type: runpod
          creds:
            type: api_key
  ```
